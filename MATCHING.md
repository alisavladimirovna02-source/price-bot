# Сопоставление по mapping.txt

Парсер при каждом запуске загружает `mapping.txt` из GitHub, указанного в
`GITHUB_REPO`, с помощью `GITHUB_TOKEN`. Локальный файл автоматически не подставляется.

Формат правила:

```text
17 512 Black eSim = iphone17black512eSIM
```

После удаления цены название должно полностью совпасть с левой частью правила.
Порядок слов сохраняется. Частичные совпадения, подбор по похожести и поиск по
каталогу не используются.

С обеих сторон одинаково игнорируются регистр, лишние пробелы, скобки и символы,
которые удаляет очистка прайса. Буквы, цифры, подчёркивание и знаки `/.,+`
сохраняются. SKU возвращается точно в написании справа от `=`.

`Актив`, `Неактив`, `б/у`, цвет, память и тип SIM остаются частью названия.
Например, правило выше не подходит к `17 512 Black (eSim) Актив`.
Для такой позиции нужно отдельное правило с её полным названием и нужным SKU.
Разные написания, например с `iPhone` и без него, также требуют отдельных правил.

Флаги извлекаются в колонку страны. Существующее определение SIM по стране
сохранено: US добавляет `esim`, CN/HK добавляют `2sim`, если название ещё не содержит
явного `eSim`, `1Sim` или `2Sim`. Если тип SIM уже написан, повторный суффикс
не добавляется. Полученное название затем проверяется на полное совпадение.

| Status | Значение |
| --- | --- |
| `OK` | Полное совпадение с одним SKU. `Score = 100`. |
| `NOT_FOUND` | Подходящего полного названия нет. SKU пустой, `Score = 0`. |
| `MAPPING_CONFLICT` | Одному полному названию назначены разные SKU. SKU пустой, `Score = 0`. |

Позиции с обоими видами ошибок записываются в `not_found.txt` и доступны через
кнопку «Не найдено». При конфликте нужно исправить противоречащие строки в GitHub:
добавление ещё одного правила не отменяет существующие. Повтор одинакового
названия с тем же SKU разрешён; разные регистры в самих SKU считаются разными
значениями.

В локальном mapping при проверке обнаружены пять конфликтующих названий:

- `MC9J4`
- `Honor 200 8/256 Green`
- `SE2 2024 44 Silver Denim ML`
- `Pro 16 MGE44 Silver`
- `Pro 14 MGDN4 Silver M5 Pro 24/1TB`

Автоматически выбирать правильный SKU для них парсер не будет.

Формат CSV и существующий выбор максимальной цены при нескольких предложениях
одного SKU сохранены. Если парсер завершился с ошибкой, бот сообщает об ошибке
и не отправляет CSV предыдущего запуска.

Проверки без Telegram и сетевых запросов:

```sh
python3 -B -m unittest -v test_parse_prices test_bot_runtime
```

Для применения изменений на сервере нужно обновить `parse_prices.py`, `bot.py`
и `requirements.txt`, установить зависимости и перезапустить бота.

## Если бот не отвечает

В `bot.py` включён журнал в stdout, который виден в Diagnostics хостинга.
Первое сообщение «Запускаю бота. Подключаюсь к Telegram...» ещё не подтверждает
соединение. После успешной инициализации выводится «Подключение к Telegram
установлено: @имя_бота», затем библиотека пишет `Application started`.

При получении сообщения или нажатии кнопки журнал показывает тип обновления,
Telegram ID отправителя и результат проверки доступа. Текст сообщений не
записывается. Токены Telegram и GitHub скрываются в журнале, включая traceback.
Ошибки запуска и обработки также выводятся в Diagnostics.

Команда `/start` отвечает «Бот на связи» разрешённому пользователю и не добавляет
команду в прайс. Если аккаунта нет в `ALLOWED_USERS`, бот сообщает об ограничении
и показывает пользователю его Telegram ID. Сам список разрешённых ID сохранён.

При запуске явно запрашиваются обновления `message` и `callback_query`, чтобы
приём сообщений и кнопок не зависел от ранее сохранённого фильтра Telegram API.

Для проверки загрузите обновлённый `bot.py` в рабочую папку приложения,
перезапустите его и отправьте `/start` именно тому боту, чьё имя показано в
Diagnostics. Если ответа нет, новые строки журнала помогут определить причину.
